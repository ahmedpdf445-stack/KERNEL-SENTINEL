# Architecture and telemetry contract

## Components and flow

`simulator.generator` builds a seeded workload and injected loss/malformed inputs. `telemetry.schema` validates event and loss-report records. `EventPipeline` consumes records in timestamp order, groups them into UTC minute buckets, updates the process graph, and finalizes counts when a later bucket arrives or input ends. Per-feature CUSUM detectors emit evidence-linked alerts. `evaluation.metrics` compares event IDs in alert evidence with evaluation labels. `cli` exposes these functions without network services.

The process graph keys process generations by a synthetic identity (`PID@start-event-id`), tracks parent generation links, records event-to-generation associations, and reports PID reuse, missing parents/start events, duplicates, and out-of-order timestamps. The graph has a configurable hard event capacity (default 100,000); diagnostics and retained error text are capped at 100. Evidence IDs per alert are capped at 100.

## JSON Lines

An event line has `record_type: "event"`, a unique non-empty event ID, ISO-8601 timestamp with timezone, supported event type, non-negative integer process ID, nullable parent process ID, non-empty name, and `source: "simulated"`. Optional `scenario_label` is evaluation metadata. A loss line has `record_type: "loss_report"`, a timezone-aware timestamp, positive `dropped_count`, source `simulated`, and a reason. The machine-readable contract is [telemetry.schema.json](../schemas/telemetry.schema.json); runtime checks additionally reject duplicate JSON keys and unknown properties. The Python validator currently enforces the event `source` as simulated, intentionally preventing a fake live-ingestion path.

Timestamps are normalized to UTC for bucketing. Records older than an already finalized minute are rejected and diagnosed; out-of-order events within a not-yet-finalized minute are accepted but reported by the graph. A loss report marks its entire minute missing for every tracked feature, so that minute does not update baseline statistics. Malformed lines are counted and their messages are retained up to the diagnostic cap. A fully silent interval without a loss report cannot be distinguished from a legitimately empty interval; a future sensor must provide watermarks/heartbeats as well as loss reports.

## Process identity limits

The simulator's IDs and start event references make PID reuse testable, but they are not operating-system identity. Real systems need PID namespaces, boot identity, monotonic start time or kernel process cookies, and robust parent generation resolution. A PID alone is never treated as unique for process lifetime. The runtime parser limits individual JSONL records to 65,536 characters and caps identity/name/label fields.

## Future real Linux sensor contract — separate work

A separately implemented Linux sensor should emit the same event envelope with:

- monotonic capture timestamp and a wall-clock correlation timestamp (plus explicit clock domain/precision);
- host/boot and PID-namespace identity, process ID plus generation/start-time identity, and equivalent parent identity;
- event type, source/version, and enough bounded metadata for the declared detection features;
- monotonically increasing per-CPU or per-stream sequence numbers and explicit loss reports (lost count, interval, stream/CPU);
- schema/version and source metadata; any unsupported field must be rejected or versioned explicitly.

The sensor-to-pipeline adapter must convert monotonic timestamps to a consistent ordering domain and must not silently treat loss as zero events. Permissions, kernel versions, verifier constraints, and Linux deployment are outside this implementation. No eBPF code is present.
